Updated 2026-10-21 (Asia/Bangkok). **SOURCE-ONLY, NOT EXPORTED, NOT DEPLOYED.**

## Financial model / safety
A single COD remittance may cover multiple Delivery Orders; delivery COMPLETED never implies merchant receipt. The existing Phase3V single-order preview rejects batch payouts. New `functions/hybrid-billing-lalamove-batch-preview.js` adds a **READ-ONLY pure evidence-shape check**, plus a privileged read-only Firestore fixture orchestration helper. Both server resolver callbacks are test doubles today, not actual authenticated provider/bank endpoints. A source field like `authenticated:true` is insufficient to certify authenticity; future adapters must authenticate data independently through a reviewed staging connection.

The strict preview requires 2–20 unique order IDs and independent provider Order IDs; each Order must be unpaid Lalamove COD Delivery with preserved immutable delivery-completion proof. Provider payout `PAID_OUT` must include account scope, recipient hash, transfer reference SHA, unique per-order gross, fee and remitted satang allocations, aggregate gross/fees/remitted matching the allocations and a recent authenticated-look-up timestamp. Bank/Wallet external source must independently show `POSTED`, matching recipient and transfer reference, a *different* evidence digest and exactly the sum of the provider net allocation. Provider `paidOutAt` <= bank `postedAt`; no amount partial, pending transfer, duplicate Order, fee overrun or numeric imprecision allowed. Stable allocation witness sorts IDs before SHA-256. All outcomes state `canMarkPaid:false`, `canIssueInvoice:false`, `coverageCertified:false`, `sourceAttested:false`.

## DEMO Firestore replay reservation
`functions/hybrid-billing-demo-batch-reservation.js` is explicitly restricted to `GCLOUD_PROJECT=demo-penguin-hybrid-uat` and loopback `FIRESTORE_EMULATOR_HOST`, not exported by `functions/index.js`. After read-only preview and privilege checks, a single Firestore transaction re-reads active hybrid tenant, active Super Admin, EACH source Order and immutable delivery-completion proof, a tenant batch candidate, global transfer-reference claim and tenant-local per-order reference claims. Exactly one atomic CREATE for each batch + global transfer + each order claim; repeat with identical witness returns idempotent read, conflicting transfer/Order/batch denies. This is only a `pending_independent_review` reservation; by design the proof is still **untrusted mock evidence**. No real financial posting, paid state or journal, and no legal credit/debit note is generated.

Hardcoded false in candidate: `sourceAttested:false`, `bankCreditVerified:false`, `settlementPosted:false`, `paidOrdersChanged:false`, `canMarkPaid:false`, `canIssueInvoice:false`, `coverageCertified:false`. No production scope. A client cannot invoke this route. Production Functions Auth/App Check, independent provider/financial signatures, source writer completeness and multi-day immutable ledger are NOT solved. The bank and provider replies can be forged by a bad future adapter; strict data matching alone cannot prove actual cash.
